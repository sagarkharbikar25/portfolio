BACKEND CASE STUDY

Digital Document Service Portal: Architecture & Trade-Offs

Role: Lead Backend Architect Stack: Node.js, Express, MongoDB/Postgres, JWT Outcome: 1st Prize Mini Project Competition

1. Context & Operational Constraints

Academic document requests (character certificates, provisional degrees, bonafides) traditionally moved through paper files across college departments. When physical documents were routed between clerks, verifiers, and the dean, applicants had zero visibility into status, bottlenecks were untraceable, and dispute resolution lacked an audit log.

  • Pilot Scale: Deployed across 4 academic departments serving ~1,200 student requests during pilot evaluation.
  • Constraints: Zero budget for proprietary software, needed zero-data-loss transition guarantees, and had to enforce strict role boundaries on shared workstations.

3. Three Key Engineering Decisions & Trade-Offs

Decision 1: Precondition in Query vs. Read-Modify-Write

In high-volume state transitions, fetching a document and modifying its state in application memory (doc.state = 'APPROVED'; await doc.save()) creates a critical race condition: two verifiers approving at the same microsecond can both pass validation. 

// Precondition lives in the query — the database acts as the atomic arbiter
async function transition(docId, fromState, toState, actorId) {
  if (!ALLOWED[fromState]?.includes(toState)) {
    throw new InvalidTransitionError(fromState, toState);
  }

  const doc = await Document.findOneAndUpdate(
    { _id: docId, state: fromState },
    {
      $set: { state: toState },
      $push: { history: { from: fromState, to: toState, actor: actorId, at: new Date() } }
    },
    { new: true }
  );

  if (!doc) throw new ConflictError('Concurrent modification or invalid state transition');
  return doc;
}

Decision 2: Audit Trail Atomicity ($push vs. Separate Collection)

Strategy Pros Cons & Trade-Offs
Embedded History ($push) [Chosen] Atomicity guaranteed with document update; zero transaction latency. Array growth unbounded over infinite updates (bounded to max 6 lifecycle steps here).
Multi-Document Transaction Queryable independent audit collection. Requires replica-set overhead & higher latency for college-tier database.

Decision 3: JWT Role Scoping vs. Live DB Lookups

Roles (Applicant, Clerk, Verifier, Admin) are encoded directly inside short-lived JWTs (15 min expiry) with refresh token rotation. This eliminated 1,000+ DB lookup queries/minute during peak hours while bounding role revocation lag to the 15-minute window.

4. Failure Mode & Post-Mortem

The Bug: During the pilot, an edge-case was reported where a clerk marked a document as "UNDER_REVIEW" while the applicant simultaneously amended their file, causing the amendment to overwrite verified state.

The Fix: Implemented strict versioning preconditions ({ _id: id, state: 'SUBMITTED', version: currentVersion }) so amendments automatically reject if status advancement is in progress.

5. What I Would Architect Differently Today

  • Async Notification Queue: Move Twilio/Email notification dispatches into a Redis/BullMQ worker rather than blocking HTTP responses.
  • PostgreSQL Schema Enforcement: Use relational Postgres with native foreign key and check constraints for even stricter tabular integrity across departments.

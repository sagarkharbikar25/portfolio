How I Think About Backend

I approach backend development as an engineering discipline — not just writing code that works, but building systems that handle failure gracefully, scale without rewriting, and remain maintainable six months later.

My work centers on Java and Spring Boot ecosystems, where I design RESTful APIs with proper status codes and error contracts, normalize databases to eliminate redundancy while indexing for read performance, and implement role-based access controls that map cleanly to business requirements.

I think in terms of data flow: how a request enters the system, gets validated, hits the service layer, interacts with the database, and returns a well-structured response. Every layer has a responsibility, and I keep them separated.

Featured Project 01

Digital Document Service Portal

Problem

Government and institutional offices handle document requests (certificates, verifications, permits) through manual, paper-based workflows. Requests get lost, status tracking is nonexistent for applicants, and there's no audit trail for administrative accountability. The system needed to digitize the entire lifecycle — from request submission to multi-level verification to final document issuance.

Backend Architecture

  • Role-Based Access Control (RBAC): Implemented four distinct roles — Applicant, Clerk, Verifier, Admin — each with scoped API access. Used Spring Security with method-level authorization (@PreAuthorize) to enforce permissions. Clerks can update request status but cannot approve; Verifiers can approve but cannot modify applicant data.
  • State Machine for Document Lifecycle: Each document request transitions through defined states: SUBMITTED → UNDER_REVIEW → VERIFIED → APPROVED → ISSUED / REJECTED. Invalid transitions are rejected at the service layer, preventing data corruption from malformed API calls.
  • Audit Logging: Every state change writes to an audit table with timestamp, actor ID, previous state, and new state. This provides a complete, queryable trail for compliance and dispute resolution.
  • Database Design: Normalized schema across users, roles, document_requests, document_types, audit_logs, and verification_steps tables. Used foreign key constraints and indexed on (status, created_date) for the admin dashboard queries that filter by state and date range.

Inventory Management REST API

Problem

Small warehouses track inventory in spreadsheets — no concurrent access handling, no validation, no history of stock changes. Needed a centralized API backend where multiple warehouse clients could manage products, track stock levels, and get alerts on low inventory with full CRUD operations and data validation.

Backend Architecture

  • RESTful CRUD with Validation: Built endpoints for products, categories, and stock movements. Used Bean Validation (@Valid, @NotNull, @Min) at the controller layer to reject malformed requests before they reach the service layer.
  • Optimistic Locking: Used @Version annotation on the Product entity to prevent lost updates when two warehouse operators modify the same product concurrently. The second write fails with a conflict response instead of silently overwriting.
  • Pagination & Filtering: Implemented cursor-based pagination for product listings and filtering by category, stock range, and last-updated date using Spring Data JPA Specifications for composable query predicates.

03

JWT Authentication Microservice

Problem

Multiple internal applications each implemented their own authentication — inconsistent password policies, no token expiration, session data stored in memory. Built a standalone auth service that any internal application can integrate with via API, providing centralized user management and token-based authentication.

Backend Architecture

  • JWT with Refresh Token Rotation: Access tokens expire in 15 minutes. Refresh tokens are single-use — each refresh request invalidates the old token and issues a new pair. Stolen refresh tokens become detectable because reuse triggers automatic revocation of the entire token family.
  • Password Security: Passwords hashed with BCrypt (cost factor 12). Enforced minimum complexity at the API level. Failed login attempts tracked per account with progressive lockout (5 failures = 15-minute lock).
  • Stateless Session Design: No server-side session storage. All authorization data encoded in the JWT claims (user ID, roles, permissions). The service validates tokens using HMAC-SHA256 signatures without database lookups on every request.

04

URL Shortener with Analytics

Problem

Marketing teams share campaign links across channels but have no visibility into click-through rates per channel. Built a URL shortening service with per-link analytics — click counts, referrer tracking, geographic breakdown — exposed through a dashboard API.

Backend Architecture

  • Base62 Encoding for Short Codes: Auto-incremented database IDs encoded to Base62 strings (a-z, A-Z, 0-9) to generate short, collision-free URL slugs. A 6-character slug supports 56+ billion unique URLs.
  • Async Click Tracking: Redirect responses return immediately (HTTP 302). Click metadata (timestamp, User-Agent, referrer, IP-derived geo) is written asynchronously to avoid adding latency to the redirect path.
  • Aggregation Queries: Analytics API returns pre-aggregated data — clicks grouped by day, by referrer domain, and by country — using indexed SQL queries against the click_events table partitioned by month.
